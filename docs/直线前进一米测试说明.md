# 直线前进一米测试说明

## 目标

用于测试底盘是否能沿前向直线稳定前进约 1 米。

当前推荐走自动目标链路：

`/auto/goal_pose -> vision_catch_controller_node -> /cmd_vel_remote -> cmd_vel_mux_node -> /cmd_vel -> omni_chassis_control_node -> motor_control_node`

## 测试命令

> 说明：下面这个目标是**绝对目标点**，不是速度命令。
> 默认假设当前机器人在 `vision_world` 坐标系下接近原点附近。

```bash
ros2 topic pub -r 10 /auto/goal_pose geometry_msgs/msg/PoseStamped "{header: {frame_id: 'vision_world'}, pose: {position: {x: 1.0, y: 0.0, z: 0.0}, orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}}}"
```

运行方式：

- 连续发布，频率 `10 Hz`
- 观察底盘是否沿前向走直
- 接近 1 米位置后按 `Ctrl+C`

## 命令解释

### topic

- `/auto/goal_pose`
- 类型：`geometry_msgs/msg/PoseStamped`

这是给自动控制节点的目标位姿输入。

### `header.frame_id: 'vision_world'`

表示目标点是在 `vision_world` 坐标系下表达的。

### `position.x: 1.0`

表示目标点前向坐标为 `1.0 m`。

如果当前机器人起点在原点附近，那么它会尝试向前走约 `1 米`。

### `position.y: 0.0`

表示目标点没有侧向偏移。

也就是目标希望机器人尽量沿直线前进，而不是斜走。

### `orientation`

当前 `vision_catch_controller_node` 主要只使用：

- `position.x`
- `position.y`

姿态字段当前基本不参与控制，因此这里统一使用单位四元数：

- `x=0`
- `y=0`
- `z=0`
- `w=1`

## 前提条件

测试前请确认这些节点已经启动：

- `motor_control_node`
- `omni_chassis_control_node`
- `cmd_vel_mux_node`
- `vision_catch_controller_node`

并且：

- `cmd_vel_mux_node` 当前选中 `remote`
- `/odom` 正常更新
- 目标坐标系和当前里程计原点理解一致

## 停止方法

### 方法一：停止目标发布

按 `Ctrl+C` 停掉上面的连续发布命令。

### 方法二：主动发零速

如果希望更明确地停车，可以补发一条零速命令：

```bash
ros2 topic pub --once /cmd_vel_remote geometry_msgs/msg/Twist "{linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}"
```

## 注意事项

### 1. 这是绝对目标，不是相对位移

如果机器人当前不在原点，`x=1.0, y=0.0` 表示去世界坐标中的该点，
不一定等于“从当前位置再往前走 1 米”。

同理：

- `x=-1.0, y=0.0` 的含义是“去世界坐标点 `(-1, 0)`”
- **不是**“按当前车头方向后退 1 米”

如果当前机器人已经不在 `x` 轴上，或者当前车头 yaw 已经偏了，
那么去 `(-1, 0)` 本来就会表现成一条世界坐标里的斜线。

### 2. 如果想做更纯粹的运动学测试

也可以直接发速度命令测试：

```bash
ros2 topic pub -r 10 /cmd_vel_remote geometry_msgs/msg/Twist "{linear: {x: 0.10, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}"
```

这个更适合测试“是否直线前进”，但它不是“精确前进 1 米”。

### 3. 如果出现走偏

优先检查：

- 四轮驱动方向是否正确
- `/odom` 是否漂移
- `can_1` 上的 GM3508 是否真实执行
- 地面摩擦和底盘安装是否对称

## 2026-05-07 本轮排障结论

本轮排障已确认并修复一个关键软件问题：

- `omni_chassis_control_node` 在**逆运动学**前正确做了 ROS 坐标系到运动学坐标系的转换
- 但在**正运动学**后直接把运动学输出当成 ROS `/odom` 使用，缺少反向转换

修复点位于：

- `src/motor_control_ros2/src/omni_chassis_control_node.cpp`

修复后的关键关系是：

$$
ros\_vx = kin\_vy
$$

$$
ros\_vy = -kin\_vx
$$

修复效果：

- 开环 `/cmd_vel_remote linear.x=0.1` 测试中，`/odom` 已从“主要沿 y 漂移”变成“主要沿 x 前进”
- 闭环 `/auto/goal_pose` 测试中，`vision_catch_controller_node` 输出的 `linear.y` 已接近 0，说明闭环不再错误地加入明显侧向修正

当前仍可能存在少量体感跑偏，但优先怀疑：

- 轮组一致性
- 轮径/安装角误差
- 地面摩擦差异
- 当前控制器没有主动航向保持

而不再优先怀疑 `/odom` 坐标轴映射本身。

## 推荐：按当前姿态前进/后退 1 米

如果你要测试的是：

- “按当前车头方向前进 1 米”
- “按当前车头方向后退 1 米”

那么不应直接写固定世界点 `x=1.0` 或 `x=-1.0`，
而应先读当前 `/odom`，再把相对位移换算成 `vision_world` 绝对点。

### 按当前姿态前进 1 米

```bash
python3 - <<'PY'
import subprocess, re, math, os

txt = subprocess.check_output(["ros2", "topic", "echo", "/odom", "--once"], text=True)

pm = re.search(r"position:\s*\n\s*x:\s*([-0-9.eE]+)\s*\n\s*y:\s*([-0-9.eE]+)", txt)
qm = re.search(r"orientation:\s*\n\s*x:\s*([-0-9.eE]+)\s*\n\s*y:\s*([-0-9.eE]+)\s*\n\s*z:\s*([-0-9.eE]+)\s*\n\s*w:\s*([-0-9.eE]+)", txt)

x = float(pm.group(1))
y = float(pm.group(2))
qx, qy, qz, qw = map(float, qm.groups())
yaw = math.atan2(2*(qw*qz + qx*qy), 1 - 2*(qy*qy + qz*qz))

goal_x = x + math.cos(yaw)
goal_y = y + math.sin(yaw)

cmd = f"""ros2 topic pub /auto/goal_pose geometry_msgs/msg/PoseStamped "{{header: {{frame_id: 'vision_world'}}, pose: {{position: {{x: {goal_x}, y: {goal_y}, z: 0.0}}, orientation: {{x: 0.0, y: 0.0, z: 0.0, w: 1.0}}}}}}" -r 10"""
print(cmd)
os.system(cmd)
PY
```

### 按当前姿态后退 1 米

```bash
python3 - <<'PY'
import subprocess, re, math, os

txt = subprocess.check_output(["ros2", "topic", "echo", "/odom", "--once"], text=True)

pm = re.search(r"position:\s*\n\s*x:\s*([-0-9.eE]+)\s*\n\s*y:\s*([-0-9.eE]+)", txt)
qm = re.search(r"orientation:\s*\n\s*x:\s*([-0-9.eE]+)\s*\n\s*y:\s*([-0-9.eE]+)\s*\n\s*z:\s*([-0-9.eE]+)\s*\n\s*w:\s*([-0-9.eE]+)", txt)

x = float(pm.group(1))
y = float(pm.group(2))
qx, qy, qz, qw = map(float, qm.groups())
yaw = math.atan2(2*(qw*qz + qx*qy), 1 - 2*(qy*qy + qz*qz))

goal_x = x - math.cos(yaw)
goal_y = y - math.sin(yaw)

cmd = f"""ros2 topic pub /auto/goal_pose geometry_msgs/msg/PoseStamped "{{header: {{frame_id: 'vision_world'}}, pose: {{position: {{x: {goal_x}, y: {goal_y}, z: 0.0}}, orientation: {{x: 0.0, y: 0.0, z: 0.0, w: 1.0}}}}}}" -r 10"""
print(cmd)
os.system(cmd)
PY
```

## 如何正确理解“看起来斜着走”

如果当前机器人 yaw 不为 0，
那么“按当前姿态前进 1 米”在 `vision_world` 坐标系下本来就通常不是纯 `x` 方向直线。

这时应该区分两种观察方式：

- **世界坐标系**：轨迹可能是斜线
- **车体坐标系**：只要 `linear.y` 接近 0，且位移投影到车体系后主要是前进/后退，就说明它其实已经基本直行

本轮实测中，“按当前姿态前进 1 米”虽然在世界坐标下表现为斜线，
但投影回车体系后，前进量远大于侧移量，说明控制逻辑已基本正确。

## 如何测试 `/odom` / 世界坐标闭环误差

如果你已经确认：

- 直接发 `/cmd_vel_remote` 的前进/后退基本正常
- 但发 `/auto/goal_pose x=1.0, y=0.0` 时会斜着走或向右偏

那就说明问题更可能在：

- `/odom` 本身
- `vision_world` 与 `odom` 的对齐关系
- 点位控制闭环误差

推荐按下面 3 步测试。

### 测试 1：先做开环基线

先直接发速度命令，确认底盘纯速度直行没有大问题：

```bash
ros2 topic pub -r 10 /cmd_vel_remote geometry_msgs/msg/Twist "{linear: {x: 0.10, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}"
```

如果这一步已经明显向右偏，那问题主要在底盘层，不要急着查 `/odom`。

### 测试 2：再做点位追踪

保持机器人起点尽量接近当前局部坐标原点，连续发布目标点：

```bash
ros2 topic pub -r 10 /auto/goal_pose geometry_msgs/msg/PoseStamped "{header: {frame_id: 'vision_world'}, pose: {position: {x: 1.0, y: 0.0, z: 0.0}, orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}}}"
```

如果这一步才开始明显斜走，而测试 1 基本直，那问题大概率在闭环层。

### 测试 3：同步观察 `/odom`

点位追踪测试时，同时看 `/odom` 是否也在向右飘：

```bash
ros2 topic echo /odom
```

重点看：

- 机器人明明主要在向前，`pose.pose.position.y` 是否却不断变大/变小
- 机器人没明显转头时，`orientation` / yaw 是否在漂

### 怎么判定

#### 情况 A：`/cmd_vel_remote` 直行正常，但 `/auto/goal_pose` 斜走

说明更可能是：

- `/odom` 有横向漂移
- `vision_world` 和 `odom` 没对齐
- 点位控制正在根据错误位姿主动加入横向修正

#### 情况 B：`/cmd_vel_remote` 直行本身就偏

说明问题更偏向：

- 轮组执行不一致
- 机械安装/摩擦不对称
- 电机方向或轮序还没完全校准

#### 情况 C：`/odom` 显示自己在右飘，而车肉眼也在右飘

说明闭环误差和实际运动误差叠在一起了。

这时优先处理底盘本体，再处理定位闭环。
