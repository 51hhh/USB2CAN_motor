# `/ball/landing` 与 `/ball/realtime` 视觉接口需求确认草案

> 目的：先把当前已确认的信息写清楚，再用提问的方式收敛需求；本文档**不替你做假设**。

## 1. 当前已确认的信息

### 1.1 话题语义

- `/ball/landing`：表示**球的落点**
- `/ball/realtime`：表示**球在飞行过程中的实时点**

### 1.2 当前消息类型

这两个话题当前运行时观察到的消息类型都是：

```text
geometry_msgs/msg/PointStamped
```

结构如下：

```text
std_msgs/Header header
  builtin_interfaces/Time stamp
    int32 sec
    uint32 nanosec
  string frame_id

geometry_msgs/Point point
  float64 x
  float64 y
  float64 z
```

可以理解为：

- `header.stamp`：这一个点对应的时间戳
- `header.frame_id`：这个点所在的坐标系
- `point.x/y/z`：三维坐标数值

### 1.3 当前运行时观察

当前运行时里，这两个话题都由同一个节点发布：

```text
/goal_pose_bridge_node
```

但根据你的最新说明，**目标状态应当改为由 `vision_node` 输出**。

补充说明：

- 在 `ROS_DOMAIN_ID=42` 下，可以看到：
  - `/ball/landing`
  - `/ball/realtime`
  - 发布者均为 `/goal_pose_bridge_node`
- 但在当前观测窗口里，`ros2 topic hz` 和 `ros2 topic echo --once` **都没有收到实际样本**
- 这说明当前需要区分两件事：
  1. ROS 图里已经注册了 topic / publisher
  2. 运行时是否真的持续发出了消息

### 1.4 已确认的接口边界

根据你刚才的确认，当前目标方案已经明确为：

1. `vision_node` **直接发布** `/ball/landing` 和 `/ball/realtime`
2. 下游节点**直接订阅**这两个 topic
3. 这条链路里**不以桥接/跨域节点作为最终发布者**

## 3. 待确认问题（请逐项确认）

### 3.1 关于发布职责

2. 如果 `vision_node` 未启动，系统是否允许这两个话题暂时不存在？
3. 当前运行时里的 `/goal_pose_bridge_node` 后续是要：
   - 下线
   - 保留但不再发布这两个 topic
   - 保留用于其他链路

### 3.2 关于 `/ball/landing`

1. 已确认：`/ball/landing` **不是物理落地点**，而是**相对 `/ball/realtime` 预测后续几帧的结果**。
2. 这里还需要继续确认的是：这个“后续几帧”到底是固定帧数，还是随算法动态变化？
3. `/ball/landing` 是不是应该在每一帧都持续更新，还是只在“预测稳定后”才发布？
4. 如果当前还无法稳定给出后续帧预测，是应该：
   - 不发布
   - 继续发布最近一次结果
   - 发布一个约定的无效值
5. `point.z` 对这个“后续几帧预测点”来说，是否仍然表示预测出来的高度？
6. 这个话题的时间戳应该表示：
   - 当前输入帧的检测时刻
   - 预测结果对应的目标未来帧时刻
   - 预测输出时刻

### 3.3 关于 `/ball/realtime`

1. `/ball/realtime` 表示的是：
   - 当前检测到的球心三维位置
   - 滤波后的球位置
   - 拟合轨迹上的当前点
   - 还是别的定义？
2. 它是否要求**连续高频发布**？
3. 当球短暂丢失时，是应该：
   - 立即停止发布
   - 保留最近一帧一小段时间
   - 发布预测点补偿
4. `point.z` 在这个话题里是否必须是真实高度？
5. 是否需要保证消息严格按时间递增？

### 3.4 关于坐标系和单位

3. 这个坐标系是否已经和机器人控制使用的坐标系对齐？
4. 如果视觉内部坐标系和控制坐标系不一致，转换应该发生在：
   - `vision_node` 内部
   - 中间桥接节点
   - 消费节点内部
