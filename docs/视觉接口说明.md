# 视觉接口说明

> 面向视觉节点/上位机：说明视觉需要向底盘发布什么，底盘会反馈什么，以及当前 `vision_catch_controller_node` 如何把目标位置转换成速度命令。

## 1. 总体结论

当前给视觉的主接口是：

| 方向 | Topic | 消息类型 | 作用 |
|---|---|---|---|
| 视觉 -> 底盘闭环 | `/auto/goal_pose` | `geometry_msgs/msg/PoseStamped` | 视觉发布目标落点/等待点位置 |
| 定位 -> 视觉/控制 | `/odom` | `nav_msgs/msg/Odometry` | 底盘当前融合位置和速度 |
| 控制器 -> 速度源选择 | `/cmd_vel_remote` | `geometry_msgs/msg/Twist` | `vision_catch_controller_node` 输出的自动速度命令 |
| 速度源选择 -> 底盘 | `/cmd_vel` | `geometry_msgs/msg/Twist` | 最终进入底盘运动学控制的速度命令 |

视觉模块通常**只需要发布 `/auto/goal_pose`**。不要直接发布 `/cmd_vel`，否则会绕过位置闭环和速度源选择逻辑。

## 2. 数据流

```text
视觉节点
  │ 发布 /auto/goal_pose
  ▼
vision_catch_controller_node
  │ 订阅 /odom 当前融合位姿
  │ 根据 goal - odom 计算速度
  ▼ 发布 /cmd_vel_remote
cmd_vel_mux_node
  ▼ 输出 /cmd_vel
omni_chassis_control_node
  ▼ 输出 /dji_motor_command_advanced 驱动电机

STM32 定位板
  ▼
positioning_bridge_node
  ▼ 发布 /odom，反馈给 vision_catch_controller_node
```

## 3. 视觉发布接口：`/auto/goal_pose`

### 3.0 当前没有自定义视觉 `.msg`

当前仓库里没有单独定义 `VisionGoal.msg`、`GoalPose.msg` 这类视觉专用消息。

`/auto/goal_pose` 使用的是 ROS2 标准消息：

```text
geometry_msgs/msg/PoseStamped
```

所以你不会在本仓库的 `src/motor_control_ros2/msg/` 目录里找到这个 `.msg` 文件。它来自 ROS2 已安装包 `geometry_msgs`，代码里通过下面的头文件使用：

```cpp
#include <geometry_msgs/msg/pose_stamped.hpp>
```

对应订阅代码在 `vision_catch_controller_node.cpp` 中：

```cpp
goal_sub_ = this->create_subscription<geometry_msgs::msg::PoseStamped>(
  goal_topic_, 10,
  std::bind(&VisionCatchControllerNode::goalCallback, this, std::placeholders::_1));
```

### 3.1 Topic 和类型

```text
Topic: /auto/goal_pose
Type : geometry_msgs/msg/PoseStamped
```

这是视觉给底盘的位置目标，表示“希望底盘移动到哪个点”。

当前控制节点只使用：

```text
pose.position.x
pose.position.y
```

当前配置启用车头 yaw 控制，并使用目标方向字段作为目标车头方向：

```text
pose.orientation
```

因此单位四元数 `{z: 0, w: 1}` 表示目标车头朝世界 yaw=0，不表示“保持当前车头”。如需只控制 x/y 不控制车头，把 `yaw_hold_enabled` 改成 `false`。

### 3.2 消息结构

`geometry_msgs/msg/PoseStamped` 结构如下：

```text
std_msgs/Header header
  stamp
  frame_id

geometry_msgs/Pose pose
  geometry_msgs/Point position
    float64 x
    float64 y
    float64 z
  geometry_msgs/Quaternion orientation
    float64 x
    float64 y
    float64 z
    float64 w
```

视觉需要重点填写：

```text
header.stamp       当前时间
header.frame_id    vision_world
pose.position.x    目标点 X，单位 m
pose.position.y    目标点 Y，单位 m
pose.position.z    0.0
pose.orientation.w 1.0
```

### 3.3 坐标系约定

默认参数：

```yaml
goal_frame: "vision_world"
```

当前 `vision_catch_controller_node` **不会做 TF 坐标变换**。如果收到的 `frame_id` 不是 `vision_world`，节点只会打印 warning，但仍然直接按 `x/y` 数值使用。

因此视觉发布的目标点必须满足：

- 单位：米；
- 坐标原点：和 `/odom` 使用的局部原点一致；
- 坐标方向：和 `/odom` 的平面坐标一致；
- `x/y` 是目标点在世界/局部地图坐标中的位置，不是相机像素坐标，也不是车体坐标。

简单说：**视觉要发“底盘应该到达的 odom 平面坐标”。**

如果视觉输出的是相机坐标或像素坐标，需要先在视觉侧转换成和 `/odom` 对齐的平面坐标，再发布到 `/auto/goal_pose`。

### 3.4 `世界系`、`vision_world` 和 `odom` 的关系

这三个名字的关系如下：

| 名称 | 类型 | 当前项目中的含义 |
|---|---|---|
| 世界系 | 概念 | 固定在场地/启动点附近、不跟车移动的平面坐标系 |
| `odom` | ROS frame | `positioning_bridge_node` 发布 `/odom` 使用的局部世界系 |
| `vision_world` | 视觉目标 frame 名 | 视觉发布 `/auto/goal_pose` 时写入 `header.frame_id` 的目标坐标系名 |

当前代码里，`vision_catch_controller_node` **没有查询 TF，也没有做 `vision_world -> odom` 坐标变换**。

所以当前实际约定是：

```text
vision_world 的 x/y 数值 == odom 坐标系下的 x/y 数值
```

也就是说，视觉发出的目标点必须能直接和 `/odom` 当前点相减：

```text
dx = /auto/goal_pose.pose.position.x - /odom.pose.pose.position.x
dy = /auto/goal_pose.pose.position.y - /odom.pose.pose.position.y
```

如果视觉侧有自己的世界坐标系，但它和 `odom` 的原点、方向不一致，需要先完成标定/转换：

```text
相机坐标/视觉世界坐标 -> odom 对齐坐标 -> 发布 /auto/goal_pose
```

最稳妥的现场约定是：

1. 底盘在场地固定起点执行回零，使 `/odom` 从该点开始。
2. 视觉也以同一个起点作为自己的世界系原点。
3. 视觉 X/Y 方向和 `/odom` X/Y 方向保持一致。
4. 视觉发布 `frame_id: vision_world`，但数值按 `odom` 坐标填写。

后续如果要严格区分 `vision_world` 和 `odom`，需要增加 TF：

```text
odom -> vision_world
```

或在控制节点中显式查询 TF，把视觉目标转换到 `odom` 后再控制。

## 4. 底盘反馈接口：`/odom`

视觉或上层算法需要读取底盘当前位置时，看：

```text
Topic: /odom
Type : nav_msgs/msg/Odometry
```

关键字段：

```text
pose.pose.position.x       当前 X，单位 m
pose.pose.position.y       当前 Y，单位 m
pose.pose.orientation      当前姿态四元数，主要用于 yaw
twist.twist.linear.x       当前前后速度，单位 m/s
twist.twist.linear.y       当前左右速度，单位 m/s
twist.twist.angular.z      当前旋转角速度，单位 rad/s
```

`/odom` 由 `positioning_bridge_node` 发布，来源为 STM32 ODOM_STATE 的 `x/y/yaw`。

视觉侧如果只负责给目标点，可以不订阅 `/odom`；如果视觉需要做预测或落点修正，可以订阅 `/odom`。

## 5. 控制节点行为

节点文件：

```text
src/motor_control_ros2/src/vision_catch_controller_node.cpp
```

默认参数文件：

```text
src/motor_control_ros2/config/vision_catch_controller_params.yaml
```

默认参数：

| 参数 | 默认值 | 含义 |
|---|---:|---|
| `goal_topic` | `/auto/goal_pose` | 视觉目标点输入 |
| `odom_topic` | `/odom` | 当前融合定位输入 |
| `cmd_vel_topic` | `/cmd_vel_remote` | 自动速度输出 |
| `goal_frame` | `vision_world` | 期望目标坐标系名 |
| `control_frequency` | `50.0` | 控制频率，Hz |
| `approach_gain` | `1.0` | 旧 P 控速比例系数，仅 `speed_profile_enabled=false` 时使用 |
| `max_linear_speed` | `1.0` | 最大平移速度，m/s |
| `speed_profile_enabled` | `true` | 是否启用刹停距离速度规划 |
| `accel_limit` | `2.0` | 平移启动加速度限制，m/s² |
| `decel_limit` | `3.0` | 平移刹车减速度限制，m/s² |
| `position_tolerance` | `0.05` | 到点容差，m |
| `goal_timeout_sec` | `1.0` | 目标超时时间，s |
| `odom_timeout_sec` | `0.5` | `/odom` 超时时间，s |
| `yaw_hold_enabled` | `true` | 是否启用车头 yaw 控制 |
| `use_goal_yaw` | `true` | 是否使用目标消息里的 orientation 作为目标 yaw |
| `rotate_after_position_reached` | `true` | 到达目标点后是否继续原地对齐 yaw |
| `yaw_kp` | `1.5` | yaw 保持 P 增益 |
| `max_angular_speed` | `0.1` | 控制器输出角速度上限，rad/s |
| `yaw_cmd_sign` | `-1.0` | yaw 闭环输出方向；若 `angular.z` 正方向与 `/odom` yaw 正方向一致则设为 `1.0` |
| `yaw_tolerance_rad` | `0.03` | yaw 误差死区，rad |

默认启用刹停距离速度规划：

```text
dx = goal.x - odom.x
dy = goal.y - odom.y
distance = sqrt(dx * dx + dy * dy)
remaining = max(distance - position_tolerance, 0)
speed_target = min(max_linear_speed, sqrt(2 * decel_limit * remaining))
speed = 按 accel_limit/decel_limit 从上一帧速度逼近 speed_target
```

然后节点会结合当前 yaw，把世界坐标误差转换到底盘坐标系，输出：

```text
/cmd_vel_remote.linear.x
/cmd_vel_remote.linear.y
```

禁用 yaw 控制时，`/cmd_vel_remote.angular.z = 0.0`。

启用 yaw 保持后：

```text
/cmd_vel_remote.angular.z = yaw_kp * (target_yaw - current_yaw)
```

实际输出还会乘以 `yaw_cmd_sign`。到达目标范围内会停止平移；如果 `rotate_after_position_reached=true`，仍会在 yaw 误差超过 `yaw_tolerance_rad` 时输出 `angular.z` 修正车头。

## 6. 发布频率和超时要求

默认 `goal_timeout_sec = 1.0`，所以视觉目标超过 1 秒没更新时，控制节点会停车等待新目标。

建议视觉发布频率：

| 场景 | 建议频率 |
|---|---:|
| 静态目标点测试 | 2 Hz 以上 |
| 实时落点跟踪 | 10-30 Hz |
| 高速动态目标 | 30 Hz 以上，根据视觉实际延迟调整 |

如果只发一次目标点，车可能运动不到目标就因为目标超时而停车。测试时建议连续发布。

## 7. 最小测试命令

启动相关节点后，可以手动模拟视觉发布目标点：

```bash
source /home/toe/111/USB2CAN_motor/install/setup.zsh
ros2 topic pub /auto/goal_pose geometry_msgs/msg/PoseStamped \
"{header: {frame_id: 'vision_world'}, pose: {position: {x: 1.0, y: 0.0, z: 0.0}, orientation: {w: 1.0}}}" -r 10
```

含义：持续发布目标点 `(x=1.0m, y=0.0m)`。

观察控制节点输出：

```bash
ros2 topic echo /cmd_vel_remote
```

观察最终进入底盘的速度：

```bash
ros2 topic echo /cmd_vel
```

观察当前位置：

```bash
ros2 topic echo /odom --field pose.pose.position
```

## 8. 推荐启动顺序

实车闭环建议顺序：

1. 启动 `motor_control_node`。
2. 启动 `omni_chassis_control_node`。
3. 启动 `positioning_bridge_node`。
4. 确认 `/odom` 单发布者且稳定。
5. 启动 `cmd_vel_mux_node`，并确认自动源为 `remote`。
6. 启动 `vision_catch_controller_node`。
7. 视觉开始发布 `/auto/goal_pose`。

检查速度源选择：

```bash
ros2 param get /cmd_vel_mux_node active_source
```

如果需要切到自动源：

```bash
ros2 param set /cmd_vel_mux_node active_source remote
```

## 9. 常见问题

### 9.1 视觉发了目标点但车不动

检查：

```bash
ros2 topic echo /auto/goal_pose --once
ros2 topic echo /odom --once
ros2 topic echo /cmd_vel_remote --once
ros2 topic echo /cmd_vel --once
ros2 param get /cmd_vel_mux_node active_source
```

常见原因：

- `/odom` 没有数据；
- `/auto/goal_pose` 超过 1 秒没更新；
- `cmd_vel_mux_node` 当前不是 `remote` 源；
- 目标点已经在 `position_tolerance` 范围内；
- `/odom` 有多个 publisher，当前位置跳变。

### 9.2 视觉坐标和底盘运动方向不一致

当前没有 TF 自动转换，优先确认：

- 视觉发布的是米，不是像素；
- 视觉坐标原点和 `/odom` 原点一致；
- 视觉 X/Y 方向和 `/odom` X/Y 方向一致；
- 回零后再开始发布目标点。

### 9.3 想控制朝向

当前配置使用目标姿态控制车头：

```yaml
yaw_hold_enabled: true
use_goal_yaw: true
```

视觉需要在 `/auto/goal_pose.pose.orientation` 填目标 yaw 对应的四元数。若只想控制平移、不想控制朝向，把 `yaw_hold_enabled` 改成 `false`。

注意：底盘节点还有一层 `max_angular_velocity` 限速，配置在：

```text
src/motor_control_ros2/config/omni_chassis_params.yaml
```

## 10. 给视觉侧的最小约定

视觉侧只要满足下面这几条，就能接入当前底盘闭环：

1. 发布 `/auto/goal_pose`。
2. 消息类型使用 `geometry_msgs/msg/PoseStamped`。
3. `frame_id` 填 `vision_world`。
4. `pose.position.x/y` 是和 `/odom` 对齐的平面目标坐标，单位 m。
5. 持续发布，推荐 10 Hz 以上。
6. 不直接发布 `/cmd_vel`。
7. 默认不需要填目标朝向；如果同时启用 `yaw_hold_enabled` 和 `use_goal_yaw`，再填写 `pose.orientation`。
